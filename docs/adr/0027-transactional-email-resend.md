# ADR 0027: Transactional email via Resend; verification unlocks account linking

**Status:** Accepted (2026-08)

## Context

[ADR 0026](0026-social-signin-google-github.md) shipped Google/GitHub sign-in on better-auth's default linking protection: implicit linking requires the _local_ user to be `emailVerified`, and password users never were (no verification flow existed), so OAuth sign-in on a password account's email always failed `account_not_linked` — real friction hit immediately in production testing. Fixing it properly means verifying emails, which (together with the obviously-missing password reset) requires a transactional email sender — a capability Mercury did not have in any form. The provider decision had been deferred once already (reminder emails, `reminders-core`'s header comment); this feature forces it.

## Decision

- **Resend is the email provider** — chosen over Aliyun DirectMail for integration simplicity (official SDK, generous free tier) at the current scale; deliverability to mainland inboxes is accepted as weaker and revisiting the provider (or adding DirectMail behind the same facade) stays open if qq/163 delivery proves bad. Resend is also the designated channel for future reminder emails — `src/lib/email/` is written for that reuse, but reminders stay in-app this round.
- **A single non-blank `RESEND_API_KEY` is the feature flag** (`isEmailEnabled`, `src/lib/email/enabled.ts`). When set: password sign-up requires email verification (`requireEmailVerification`), unverified sign-in gets a 403 with an auto-resent link (`sendOnSignIn`), clicking the link signs the user in (`autoSignInAfterVerification`), and password reset is live. When unset: auth behaves exactly as before. The conditionality is a hard requirement, not a convenience — `requireEmailVerification` makes sign-up return `{token: null}` with **no session**, which would break the browser e2e suite, `apiSignUp`'s `set-auth-token` assertion, and the native bearer contract in keyless environments. `MERCURY_EMAIL_FROM` is optional with a prod default (a second required var would only add a way to silently ship with email off).
- **Linking is unlocked by defaults, not config.** No `accountLinking` block: better-auth's gate — (IdP-verified email) AND (local `emailVerified`) — now passes for verified password users, and keeps blocking unverified ones, which is exactly the anti-takeover property ADR 0026 chose. No schema change anywhere in this feature.
- **`revokeSessionsOnPasswordReset: true`** — a stolen session must not survive a reset. Related bonus, documented as the intended flow: `resetPassword` creates a credential account when none exists, so OAuth-only users "set a password" through the same forgot-password flow (settings links them there).
- **`sendEmail` never throws** (`src/lib/email/send.ts`): a Resend outage degrades to a check-inbox screen without an email plus a working resend button, instead of a 500 on sign-up; it also keeps `requestPasswordReset`'s constant-time "sent if registered" envelope constant. Failures are logged server-side.
- **`/verify-email` is a dedicated public page** (with `/forgot-password` and `/reset-password`, all 404 when keyless): better-auth redirects verification failures to the callback URL with `?error=`, and `src/proxy.ts`'s login bounce for protected paths drops query strings — pointing the callback at `/dashboard` would silently eat error states. Templates are bilingual zh+en in one body; the better-auth send callbacks carry no locale and two short emails don't justify plumbing it.
- **Preview deploys stay keyless against the prod database** — sign-ups there skip verification. Accepted: linking still requires a verified email so there is no takeover path, previews are already non-functional (Neon branch quota), and scoping the key to Production keeps the blast radius of a leaked preview URL at zero emails sent.

## Consequences

- Operators enable per environment: verify the sending domain in Resend (DKIM/SPF/Return-Path DNS on `mercury.ainaive.com`), set `RESEND_API_KEY` in Vercel Production. Existing unverified password users get a 403 plus a fresh verification email on their next sign-in — acceptable at the current user count.
- The native API contract changes when enforcement is on: `POST /api/auth/sign-up/email` returns `token: null` (no `set-auth-token`); clients wait for web-link verification, then sign in. Documented in docs/API.md; `/api/auth/*` stays exempt from the OpenAPI drift guard.
- Settings gains change-password and linked-accounts sections (`listAccounts`/`linkSocial`/`unlinkAccount`; better-auth's `allowUnlinkingAll: false` default guards the last sign-in method server-side).
- Future work now cheap: reminder emails (reuse `sendEmail` + `reminders-core`), change-email with confirmation, native idToken social sign-in.
