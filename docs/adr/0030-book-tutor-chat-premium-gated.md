# ADR 0030: Book tutor chat — premium-gated runtime AI in the reader

**Status:** Accepted (2026-08) — amends the _scope wording_ of [ADR 0024](0024-book-reading-pregenerated-recall.md) ("runtime never calls AI for books"); its actual decision — runtime never _generates book questions_ — stands unchanged. First use of the hard-gate recipe reserved in [ADR 0025](0025-membership-roles-and-tiers.md); reuses the chat machinery of [ADR 0013](0013-tutor-chat-single-thread-non-streaming.md).

## Context

The book reader is the app's long-tail habit surface, and reading an original novel in a second language is exactly where a learner stalls: an opaque sentence, a lost plot thread, no one to ask. An in-reader AI coach — ask about a selected sentence, get unstuck, be nudged to keep going — is both a retention mechanic and the first genuinely premium-feeling feature (每本书都配一个私教).

ADR 0024 said "runtime never generates questions," with three rationales: zero marginal cost per reader, keyless operation (the fallback content _is_ the content), and question quality under human review. Derived docs compressed this to "runtime never calls AI for books." A conversational tutor keeps two of the three intact — it generates no questions, and keyless operation survives (the feature is simply absent) — while the zero-marginal-cost rationale is deliberately _replaced_: the premium gate plus the per-book daily cap bound the new cost instead of zero bounding it. That contradicts the compressed phrasing, so the scope needs restating: **pre-generated recall content stays AI-free at runtime; the tutor chat is the reader's one runtime AI surface, and it is premium-gated, capped, and absent keyless.**

Two integrity properties had to survive embedding an LLM in the reader:

- **Quiz integrity.** Answer keys (`correctIndex`/`explanationZh`) never reach the client (`sanitizeChapter`); an AI with the raw chapter row in its prompt would re-open that hole from the server side.
- **Spoilers.** The server's only position truth is chapter-granular (completion derives from `book_quiz_attempts`); the reader page renders a whole chapter at once, so everything in the current chapter is already on screen, and everything after it is unread.

## Decision

- **Hard premium gate, hidden for free** — the first `PremiumRequiredError` throw, exactly per ADR 0025: `Entitlements` gains `bookChatEnabled` (boolean, tier-flipped) and `bookChatDailyLimit` (single `MERCURY_BOOK_CHAT_DAILY_LIMIT`, default 50, no free/premium pair — the boolean is the gate). Free users see no entry points; the service still enforces (403 `premium_required`). Gate order is **enabled before entitled**: a keyless server reports the feature absent (503) rather than advertising a premium gate it cannot serve — so keyless e2e sees an unchanged reader, and the 403 path is only observable with an AI key. The service enforces the order by calling `bookChatGate` (the unit-tested helper IS the running gate, so the ordering cannot drift from its tests).
- **One rolling thread per (user, book)** on new tables `book_chat_messages` / `book_chat_states`, line-for-line mirrors of the ADR 0013 shapes (learner-local day cap, sequence ordering, renewable single-flight claim, atomic double-insert, failed calls consume nothing). The existing `chat_states` cannot host this — its PK is `userId` alone. `chapterId` stamps each message and rides the same composite FK as `book_quiz_attempts`, so a chapter reseed cascades chat history away (accepted; same blast radius as attempts). Chatting records streak activity like the main tutor.
- **The cap is per (user, book) per day.** Worst case = limit × library size (7 seeded books). A global cap would need multi-row locking or a separate per-user quota row; deliberately deferred while the library is curated and small.
- **The spoiler/answer guards are structural first, behavioral second.** `buildBookChatContext`'s input type has no slot for check-ins, quiz items, or answers — sections enter as bare `text`, prior chapters as title + `summaryZh` only, hard-filtered to the reader's **exposure frontier** — the furthest chapter the server can prove they have seen: completed quizzes, chapters they chatted from (chatting is only possible from that chapter's page), and the visited chapter itself. Revisiting an earlier chapter therefore keeps every seen chapter's summary in context, so the per-book thread's own history — which may discuss them — stays coherent. Book prose runs through `sanitizeUntrusted` so it cannot close delimiter tags. On top of that, `bookTutorSystemPrompt` adds behavior: never discuss beyond the current chapter (deflect forward questions toward reading on), never resolve MCQ-shaped questions (quiz stems are client-visible and can be pasted — coach from the passage instead), and always push toward finishing the book. The guards protect the product loop, not exam integrity — any score completes a chapter (ADR 0024), and a determined reader can always ask an external AI.
- **Transport and UI reuse the established patterns**: service + thin server action (union result, new `premium_required` arm) + `GET/POST /api/v1/books/{bookId}/chat/messages` (`chapterId` in the body; GET is never premium-gated — `entitled: false` is data, and a downgraded user keeps read access to their history). The chattable set is **seeded books ∪ (future BYOB) the user's own** — enforced in the context query before the lock check and the quota claim, so a foreign user-owned book can never reach the provider and always answers an opaque 404 (a lock check first would leak existence via 409 chapter_locked). The UI is a docked corner panel mounted in `BookReaderRunner`'s reading branch, so quiz mode unmounts it; a text-selection affordance quotes the selection into the composer as a `「…」` prefix on the same content string (nothing new to persist), and a quote sent alone is an explain-this-passage request.

## Consequences

- Reader marginal cost is no longer zero — but only for premium users, bounded by `cap × (context + 1024 output tokens)` per book per day, with the whole current chapter in the system prompt (cache-friendly across a chapter's turns; largest seeded chapter ≈ 49k chars — `gg-ch-07` — against a 60k safety valve, and a content guard test asserts every chapter fits so the valve never fires on shipped prose).
- Single-flight is per (user, book), so one premium user can hold up to library-size concurrent provider calls (7 today, plus the main tutor's one). Accepted at this scale — premium is admin-granted — but a global per-user lease must be revisited alongside the cap scoping if BYOB lands.
- AGENTS.md / ARCHITECTURE.md rephrase their book bullet: runtime never _generates book questions_; the premium tutor chat is the reader's one runtime AI surface.
- Section-level position tracking (`book_reading_positions`) stays future work; the spoiler boundary is the chapter, which matches what the page shows anyway.
- BYOB (ADR 0024's deferred premium split) remains open; if it lands, per-book caps multiply by user-owned books and the cap scoping decision above must be revisited.
